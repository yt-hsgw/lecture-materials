01.

良い PR / 悪い PR を 並べる

体感

3つ の シナリオ で 比較

同じ 「機能追加」 でも、 タイトル ／ 本文 ／ サイズ で **レビューしやすさ** が 激変。 左 が 悪い 例、 右 が 良い 例。 下 の チェック項目 で 違い を 言語化。

❌ 悪い PR

✅ 良い PR

02.

レビュー コメント の トーン

ハンズオン

どれが 「良い」 レビュー？

同じ 指摘 でも 言い方 で チーム の 雰囲気 が 変わります。 5問 解いて 「nit / suggestion / must / harsh」 の 違い を 体感。

問題 1 / 5 — スコア: 0
03.

ブランチ戦略 比較

体感

GitHub Flow / Git Flow / Trunk-based

3つ の 戦略 を SVG 図 で 比較。 タブ で 切り替え、 各々 の メリット ／ デメリット ／ 向く チーム規模 を 確認。

04.

Conventional Commits ジェネレータ

ハンズオン

標準形式 で コミット を 書く

type / scope / subject / body / breaking change を 入力 する と、 type(scope): subject 形式 が 自動 生成 されます。 リリースノート / SemVer 自動化 と 相性 抜群。

05.

クイズ で ふり返ろう

3問チャレンジ

Q1. 5人 チーム / 週1リリース の Web サービス に **おすすめ** の ブランチ戦略 は？
💡 5人 / 週1 は GitHub Flow の ど真ん中。 Git Flow は オーバースペック、 Trunk-based は Feature Flag 基盤 が 重い。
Q2. レビュー コメント の 「**must:**」 を 多用 する 弊害 は？
💡 must は 厳選、 nit / suggestion を 多用。 「コード を 批判 する のであって 人 を 批判 しない」 が 鉄則。
Q3. Conventional Commits の **主な メリット** は？
💡 release-please / semantic-release が type を 元に 自動 で バージョン を 上げ、 リリースノート を 生成。
06.

きょうのまとめ

おぼえたこと

1

📋 良い PR ＝ 小さい / 1目的 / 「なぜ」

300行以下、 タイトル一文、 What / Why / How、 スクショ ／ テスト。

2

💬 レビュー は コード を 批判、 人 を 批判 しない

nit: / suggestion: / must: の 重大度 ラベル で トーン を 制御。

3

🌳 ブランチ戦略 は 状況 で 選ぶ

5〜20人 ＝ GitHub Flow、 大規模 製品 ＝ Git Flow、 巨大 ＝ Trunk-based。
