01.

N+1 クエリ ベンチマーク

体感

ループ fetch vs JOIN を 比較

100件 の ユーザー の 「投稿数」 を 取得 する 2方式 を シミュレート。 ループ fetch ＝ N+1 クエリ、 JOIN ＝ 1クエリ。 ユーザー数 を 変えて 体感。

ms

❌ N+1（ループ fetch）

const users = await db.select().from(users);
for (const u of users) {
  u.postCount = await db.count(posts)
    .where(eq(posts.userId, u.id));
}

✅ JOIN（1クエリ）

const users = await db.select({
  user: users,
  cnt: count(posts.id)
}).from(users)
  .leftJoin(posts, eq(posts.userId, users.id))
  .groupBy(users.id);

💡 注意

インデックス は 追加すれば 速くなる魔法 ではない: 書き込み（INSERT/UPDATE）が 遅くなる、 ディスク 食う、 WHERE LOWER(email) や LIKE '%foo%' では 効かない。 EXPLAIN ANALYZE で 確認。

05.

クイズ で ふり返ろう

3問チャレンジ

Q1. N+1 クエリ の **主な 原因** は？
💡 「親 を 1回 取得 → 子供 を N回 取得」 で 1+N クエリ。 JOIN / include / 一括取得 で 1クエリ に。
Q2. 1000万件 の テーブル で `WHERE email = ?` を **数 ms** で 引く には？
💡 B-tree インデックス で O(log n)。 1000万 → log₂ ≒ 23ステップ で 完了。
Q3. **本番 で 危険** な マイグレーション は？
💡 NOT NULL 追加 は 既存 行 を 全て 書き換える → ロック / 長時間 ダウン。 Expand-and-contract（add → backfill → switch → drop）で 段階的 に。
06.

きょうのまとめ

おぼえたこと

1

🐌 N+1 を 倒す

ループ fetch を JOIN / include / DataLoader で 1クエリ に。 ORM の 罠 に 注意。

2

⚡ インデックス で O(log n)

WHERE / ORDER BY / JOIN で 使う カラム に。 ただし 書き込み 性能 と トレードオフ。

3

🔴 Cache-aside ＋ 無効化

Redis で hot path を 守る。 TTL ＋ 明示 invalidate の 併用 が 現実解。

4

🚦 マイグレ は Expand-and-contract

破壊的変更 は 段階的 に。 後方互換 を 保ちながら デプロイ → 移行 → 削除。
